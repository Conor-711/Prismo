# X 每日数据包工作流

更新：2026-09-10。用户每天提供一次 X 数据包；在本机处理，在现有 Client API 的 PostgreSQL 发布。不是每天重打包 iOS，也不启动新的爬虫、网页构建或自动交易。

## 给后续对话的执行约定

当用户说“更新今天的推特数据”并提供文件时，按本文执行。先确认包的时间、规模和来源，再处理、校验、发布，最后回报实际状态。`inspected` / `ready` / `published` 是不同状态，不能把本地 JSON 更新称为已经上线。没有新包时不要把旧快照重新发布冒充当日数据。

## 首次接通

1. 用户先安装包含本次客户端刷新修复的内测版本，以后相同接口的数据更新不需要升级 App。
2. 内测使用 `bSmart Internal Alpha` scheme，当前 URL 为 `https://api.158-247-196-93.sslip.io`，环境必须是 `production`，不能使用 `--use-fixture-data`。普通 Release 默认的 `api.bsmart.today` 在本次检查中未能解析，域名完成配置前不要误选它。
3. 服务端安装本次 Client API 代码及 requirements。已有 read-model 表由原部署提供；新命令不建表、不改 schema。缺表/缺列时停下，由用户执行已有迁移，不能自动补库。
4. 日更包和实时 X worker 不应同时作为 X 数据的写入方。切换时先停用实时 X 发布任务，将对应运行环境的 `X_INGEST_ENABLED=false`；Smart Money worker 不受影响。发布命令会检查该开关，但仍需运维确认另一个写入进程实际停止。
5. 配置 `BSMART_READ_MODEL_DATABASE_URL` 指向线上 read-model PostgreSQL。凭据只从环境或受保护的环境文件读取，不放命令参数、Git、日志。数据库不要直接开放到公网；本地发布通过已验证的 SSH 隧道，或在服务端容器内执行发布命令。
6. 首次上线要实际验证同一个已安装 App，在发布前后获得不同的作者/观点数据与更新时间，再宣布接通。

本轮连接检查：内测 HTTPS `/health` 返回 `production/database/ok`；现存项目 SSH 密钥登录 Vultr 被拒绝。因此本轮没有修改线上数据，首次线上发布尚待恢复服务器访问后完成。

## 输入

- 支持一个 JSONL 文件、包含 `tweets_*.jsonl` 的目录、或包含此类文件的 ZIP（支持嵌套目录）。
- 沿用原归档格式：`tweet_id`、带时区的 `created_at`、`author_handle`、完整 `text`；`cashtags` 为数组。`author_id`、互动数字等继续由原适配器消费。
- ZIP 拒绝越界路径、软链接；总解压声明大小不超过 2 GiB、文件不超过 5,000。先复制到隔离临时目录，再逐行检查；原始上传文件不修改。
- 以文件内容 SHA-256 的组合识别重复包；ZIP 外壳/文件名变化但内容未变时不重算。原始帖按既有 `(ticker, tweet_id)` 幂等入库，不删除历史。
- 原创、回复、引用沿用现有处理规则，纯转发不进入观点流程。作者排名和算法不变，产品最新观点继续使用各平台正式榜单 Top 25%；日更只处理 X，其他平台的数据不会被当作此次更新重新发布。

## 日常命令

先检查，不写业务数据库、不调用模型或行情接口：

```bash
make x-daily PACKAGE='/absolute/path/daily.zip'
```

确认原帖时间范围、数量、模型凭据和预算后处理：

```bash
make x-daily PACKAGE='/absolute/path/daily.zip' APPLY=1 WORKERS=2 MAX_CALLS=1000
```

同一个命令再次执行即续跑。`MAX_CALLS` 限制本包待抽取候选数量和待发布窗口的阅读行数，不是货币预算；需要与现有 provider 预算配置配合使用。超过上限先评估，不能自行无限提高额度。第一次补齐旧库的 30 天展示窗口可能比正常一天的工作量更大。

本地已配置到线上数据库的安全连接时，可合并执行：

```bash
make x-daily PACKAGE='/absolute/path/daily.zip' APPLY=1 PUBLISH=1
```

如果计算在本机、发布在 Vultr：只上传输出的 `release/`，不上传 `data/dev.db`。将此目录挂载到已更新的 Client API 容器，再执行以下模块；它使用容器现有数据库环境变量。不要对本地文件路径假定服务端也存在相同路径。

```bash
python -m services.client_api.publish_daily_x --input-dir /mounted/release
python -m services.client_api.publish_daily_x --input-dir /mounted/release --apply
```

每次发布不需要重启 API 或重新构建 App。ETag 和数据库读取立即反映提交后的新版本。

## 处理链路与闸门

1. 增量原帖导入，沿用现有启发式候选筛选；抽取仅针对本包候选，不能顺带消耗整个历史积压。
2. Call 抽取沿用现有 provider、结构与归属规则。失败/预算耗尽后检查数据库是否仍有待处理候选；只要有缺口就停止，不把退出码为 0 当作全部完成。
3. 补充已完成交易日的行情，然后对 X 历史 Call 按现有方法结算、重算 Score。保留完整历史样本，不只用当天数据排名。缺失或过期行情阻止发布，不生成假价格。
4. 对近 30 天正式 Top 25% 将进入产品的观点提炼双语摘要并补完整译文。全文翻译不截断输入，摘要与译文分离；极端压缩、缺数字、空译文会阻止发布。这些机器检查不能证明翻译语义完全准确，误报需要人工核查，不能跳过闸门伪称完整。
5. 导出作者、近 30 天观点、历史代表作，继续合并已审核的资料依据/头像/作者介绍。不额外调用全网新闻检索，也不把不存在的佐证补成事实。代表作继续沿用最多三个不同标的规则。
6. 校验文件哈希、数量、必需 iOS 字段、唯一 ID、作者引用、源数据与生成时间。源包最新时间超过 96 小时、生成超过 36 小时，默认不能当成新日更发布。输出 `daily-x-manifest.json` 才代表本地准备完成。
7. 发布器复用现有 X 事件投影生成 `portfolio-signals`，沿用确定性事件 ID。四个集合的 X 分区在同一事务替换，保留其他平台、链上数据和所有用户状态；不会顺带重建 `ticker-intelligence` 或网页快照。
8. 并发版本变化则回滚事务；任一集合减少超过 25%（原有至少十条）需先人工审查，再显式 `--allow-drop`。先保存旧 X 分区备份，提交后核对数据库哈希并生成 `publication.json`。

“日更完成”指 API 中的新数据可读。APNs 推送发送和每日摘要派发仍属于现有通知任务，本命令不会对历史补导数据自动群发通知。

## 记录与回滚

`data/runtime/x-daily/<packageHash>/` 保留 `inspection.json`、`run.json`、`release/`。`run.json` 记录源数据范围、步骤进度、数量与失败阶段；成功阶段不会重复跑，失败阶段继续增量处理。发布端 `publication.json` 记录提交时间、各集合哈希和 `rollbackDirectory`。

```bash
make client-api-publish-daily-x INPUT_DIR='/absolute/path/release/backups/<timestamp>' APPLY=1 ROLLBACK=1
```

回滚仅恢复备份的 X 内容，不回滚用户持仓、追踪、已读状态或数据库 schema。新版本已在线时，旧版本默认被拒绝，必须显式进入回滚流程。上传的新包不代表被删帖，缺失原帖不会自动从历史数据库删除；删除/更正仍走既有内容治理流程。

## iOS 获取与验收

- 启动时加载服务器数据；前台每 60 秒检查。不是承诺 App 被系统挂起/关闭时也会在后台精确到点刷新。
- 刷新包括作者排名、观点、持仓事件；已打开代表作随版本变化更新，证据独立变动最多通过五分钟刷新补获。旧请求晚到不会覆盖新请求结果。
- HTTP 条件请求复用未变化的数据；离线时保留上次成功内容和真实更新时间，不清空列表，不拿失败请求刷新更新时间。
- 首次上线检查：记录同一设备作者/观点 ID → 发布新包 → 不升级 App，回到前台 → 核对新观点、作者排名、代表作、更新时间；同时确认本地持仓成本、追踪和已读状态未变。分别检查 X/Reddit/YouTube/Smart Money。
- 当前自动测试覆盖包校验、幂等、续跑、部分失败、发布保留/回滚、HTTP 304 鉴权和 iOS 刷新。真实付费模型全链路与 Vultr 发布需要实际新包及恢复服务器权限后验收；不能由单元测试替代。

本轮另跑现有 API 回归时，三个旧用例仍依赖五条固定演示事件或 HOOD 的演示事件，而当前 fixture 只有一条事件，导致数量断言/查找失败。这不是日更发布成功的证据，也不应通过改动用户数据去迎合旧测试；此次日更测试使用隔离数据独立验证。
