# Arbitrum USDC 入金与设备钱包

> 2026-09-12 内测调整：当前 1.0(6) 取消强制助记词备份，保留可选备份入口；本机密钥、Google 身份、设备解锁和操作确认不变。Google 不提供丢失密钥的恢复。下文历史记录中的“必须先备份”以此内测例外及 `docs/contracts/native_perpetual_mvp.md` 为准；公开发布前需关闭免备份开关或另行完成可恢复钱包方案。

## 决策摘要

目标链路：Google / Apple 登录，在当前设备创建独立钱包，完成恢复准备，接收
Arbitrum One 原生 USDC，转入 Hyperliquid，然后使用真实可用余额交易。第一阶段
通过 Hyperliquid builder code 作为交易前端接入既有市场，不自建交易所、
不部署 HIP-3 市场，不做法币入金、跨链聚合或后端托管提款。
2026-09-11 用户进一步明确：**交易仅支持永续合约**，不做现货、交割合约、期权或预测市场。
首版资金只服务 USDC 保证金合约。内部 spot/shared USDC 读取与 CCTP 回退对账属于
资金处理，不能删掉，也不能据此增加现货交易入口或把回退余额当已验证的可用保证金。
研究账户、钱包控制权、资金状态、订单执行必须分别建模。

首版按照本地自托管实现：后端保存经验证的产品身份和钱包公开地址，不保存完整
私钥或助记词。登录不能替代恢复凭证，不用 OAuth token 派生密钥；新手机上缺少
钥匙时不能静默创建新钱包。这是产品身份与资金控制权不同的直接结果。

当前实现包含预生产身份、应用会话续期及撤销、Apple 原生凭据检查、后端账户删除与 Apple 主动撤权、
原生删除确认/Keychain 进度恢复/Google 撤权/本地资料清理、本地钱包创建与恢复、地址绑定、CCTP 费用预览、源链
预检/签名/提交适配器、源链与目标链回执核对、认证消息、设备加密交易日志及
按账户模式区分的 HyperCore 真实余额只读查询，以及受入金开关约束的原生收款页、
金额审核/授权/网络费签名/提交确认页。
这些不是已开放的入金产品：HyperCore 逐笔记账、真机恢复验收、真实订单、提现及
安全审计仍须完成，生产开关不能替代这些验收。

## 协议事实

Hyperliquid 最新 USDC 文档明确推荐 CCTP，并把 Bridge2 标为弃用。此前 Bridge2 的
5 USDC 最低额只适用于旧路线，不能作为新产品的通用最低额。本项目不再生成旧桥
入金计划，也不提供失败后自动改走旧桥的回退。任何合约地址都不能冒充个人收款
地址。[^1]

首版接收地址应为用户 owner EOA。Arbitrum 收到资金后，由该钱包通过 Circle
CctpExtension 发起转入，需要 Arbitrum ETH 支付 gas。界面须区分钱包收到、
跨链处理中、HyperCore 记账三个状态，不能用统一“到账”掩盖差异。[^22]

Circle 发布的 Arbitrum 原生 USDC 合约是
`0xaf88d065e77c8cC2239327C5EDb3A432268e5831`。校验固定链和完整地址，不按名称
或符号识别资产，不接受 USDC.e、其他网络 USDC 或同名假币。[^3]

CCTP 的目标是 HyperEVM，再通过 CctpForwarder / CoreDepositWallet 转入 HyperCore。
原生 USDC 保留在 HyperEVM 合约，HyperCore 中展示的是协议记账权益，不是另一份
Circle 原生代币。源链成功、目标链 mint、HyperCore 入账需要分别核验。[^24]

## 钱包架构比较

| 方案 | 密钥边界 | 恢复 | 判断 |
|---|---|---|---|
| 本地 EOA + Keychain | 用户设备，使用时短暂进入进程内存 | 独立备份与验证 | 当前主方案 |
| Privy on-device | 设备、认证、恢复份额分布于不同边界 | 自动或用户管理 | 不是“完整私钥只存本地”的同义词 |
| Turnkey enclave | 服务端隔离执行环境 | 认证与恢复集成 | 不符合当前严格本地签名要求 |
| 外接钱包 | 由钱包 App 管理 | 使用其既有恢复 | 可作为后续导入/退出路径 |

Privy 公开描述份额分布和恢复信任模型，其浏览器 iframe 说明不能直接证明原生
Swift SDK 的相同隔离保证。Turnkey 的 enclave 与可证明执行也不等于 iPhone
本地签名。采用任何托管式恢复都需要明确说明信任变化，而非只比较登录速度。[^5][^6]

Apple Secure Enclave 的相关密钥支持是 P-256，不能直接用来保存和签署 Ethereum
secp256k1 owner key。可以由 Keychain 的设备绑定与用户在场访问控制保护秘密，或
由 Enclave 保护包裹密钥，但不能宣称 Ethereum 私钥从不进入应用内存。[^7]

### 本地钱包安全要求

采用固定版本、成熟的 secp256k1、Keccak、EIP-712 库，不手写曲线算法。用系统安全
随机数生成密钥，以公开已知向量验证地址、签名恢复、低 S 和编码。私钥不能进入
UserDefaults、数据库、日志、崩溃报告、埋点、剪贴板或普通缓存。资金签名要求
设备用户在场；后台只允许公开行情、余额查询，不能悄悄签名。

创建必须先持久化密钥，再做控制权证明并绑定公开地址。网络超时重试同一地址；
不能每次启动、登录或重试都生成新钱包。内部 account ID 是本地钥匙索引；切换身份
时终止旧签名任务。注销登录与重置研究缓存都不能删除钱包。

恢复优先按用户管理的离线备份设计。开放收款前必须验证恢复能力，不能只有一个
“我已备份”复选框。新设备发现账号已有钱包但无钥匙，进入恢复，不允许覆盖旧绑定。
自动云备份和加密导出后续独立评审，不为了方便把明文或可由后端解密的备份上传。

## 账户安全

Google 使用官方 iOS SDK，后端验证 ID token，而非接收一个客户端提供的 userID。
校验固定 JWKS 签名、issuer、audience、authorized party、时间和 nonce。Apple
采用系统授权并在后端校验，不能仅在手机上解码 JWT 后判定登录。[^8][^9]

工程固定 GoogleSignIn 9.2.0，其 API 支持 nonce。10.0.0 已发布并调整依赖；不在
资金功能开发中无审查自动升级。Google access token 和 provider ID token 都不能
直接作为 bSmart 的长期 session，更不能当作钱包私钥。[^10]

身份唯一键为 `(provider, subject)`，不是邮箱。Apple 和 Google 同邮箱不自动合并，
后续关联必须重新验证双方，保护原钱包绑定。匿名研究安装会话保持独立，登录不会
静默覆盖持仓或把他人设备数据合入一个账户。

生命周期需覆盖退出全部设备、授权撤销、换机、换 Apple ID、恢复失败与账号删除。
Apple 要求支持创建账号的 App 提供应用内删除入口，并撤销 Sign in with Apple
token。删除产品账户与链上资产不是同一件事，必须提供提现/导出，不得销毁唯一钥匙。
授权码交换、加密授权凭据保存、应用会话轮换、已签名 provider 通知接收及 Apple
原生凭据检查、账户删除/Apple 主动撤权与失败恢复，以及原生删除确认、持久化查询凭据编排、
Google disconnect、本地账户资料清理已实现。过期/遗失查询凭据恢复和钱包退出链路、真实通知流、
原生系统与真机验收仍缺少证据，应用续期不等于重新验证 provider 授权，因此生产
登录仍硬性禁用。[^11][^12]

## 用户流程

### 登录

设置中的“账户与钱包”进入原生账户页，Apple / Google 同等级，用官方按钮。
研究内容保持可访问，不将首页改成强制登录屏。取消授权回到原页面；配置缺失、
过期和服务失败给出明确状态，不出现假的成功账户。

### 准备钱包

身份验证成功后自动进入钱包初始化。创建、恢复验证、地址绑定是不同阶段。
钱包锁定、设备不支持、密钥缺失必须有对应处理，不用一个无限 loading 隐藏错误。
在任何必要条件未通过前不展示收款 QR 或示例地址。

### 入金

准备完成才展示个人 EOA、QR、复制操作。网络固定 Arbitrum One，资产固定原生 USDC，
不提供容易误选的多链列表。保留必要的网络、代币、最低额风险提示，不堆叠功能教程。
资金进入钱包后，明确显示“转入 Hyperliquid”；签名前给出金额、估算 gas 和目的地。
gas 不足引导补充 ETH，不自动换币、不请求无限授权、不在余额中暗扣费用。

状态为：等待收款、钱包已收到、等待签名、链上已提交、等待 Hyperliquid 记账、可交易。
按 `chainId + txHash + logIndex + wallet` 识别事实，处理失败、重组、重复回调和重启。
提交超时先查询原交易，不能自动再转一次；余额查询失败是未知，不是零或成功。

### 交易

金额使用整数最小单位或精确十进制，USDC 六位，拒绝科学计数、超精度和溢出。
真实订单只使用对应 HyperCore 账户的真实可用余额，不能与练习账户 US$10,000 合并。
订单使用唯一客户端 ID，对不确定提交先查状态，不能盲目重发。

既有 HIP-3 市场还需要 DEX/asset ID 和保证金账户路由。默认 perp 余额不自动表示
其他 DEX 也可用，下单前核验市场 collateral 和账户状态。签名结构、nonce、过期时间
和 agent 权限应与官方 SDK 向量交叉验证，不把普通查询接口当成执行接口。[^13]

## 本地钱包实现与威胁边界

采用 Wallet Core 的 BIP39、BIP32/BIP44、Ethereum 地址和 EIP-191 实现，不自行编写
密码学。系统通过 `SecRandomCopyBytes` 产生独立 256-bit 熵；固定 24 个英文恢复词、
空额外 passphrase、`m/44'/60'/0'/0/0`。不从 Apple/Google 身份或密码派生密钥。[^16]

选用官方 4.8.1 二进制发布资产并锁定 SHA-256。实际检查发现，该源码标签的根
`Package.swift` 仍引用 4.2.9，故仓库保存官方发布 manifest 的薄封装，而不是仅标注
一个看似新的 Git tag。校验和证明下载完整性，不证明供应链未被攻破；发布前仍需
审查精确版本、依赖许可证/致谢和独立安全评估。[^17]

Keychain 保存的是等价于钱包主密钥的 BIP39 熵，不同步 iCloud，不放 UserDefaults、
研究缓存、日志或后端。使用 `WhenPasscodeSetThisDeviceOnly` 与 `userPresence`，
访问需系统授权。这里的 secp256k1 签名在进程中执行，不能宣称私钥永不进入内存，
也不能宣称 secp256k1 直接存入 Secure Enclave。Swift 字符串和 Data 可能存在复制，
临时缓冲区清理只是尽力减少暴露，不是经过证明的完全清零。[^7][^18]

钱包建立前先读取服务端的明确状态。网络故障、解码错误、Keychain 锁定/损坏不是
“没有钱包”；任何一种都不得触发新建。绑定证明包含固定受众、内部账户、地址、
链、会话关联 nonce 和五分钟期限。客户端重建限定文本，拒绝签任意服务端文本；
服务端通过独立 Python Ethereum 实现恢复地址、限制 low-s/v 编码并原子消费挑战。
这只证明地址控制权，不授权入金、划转、下单或 Builder 费用。[^19][^20]

退出或切换账户不删除密钥。两台设备竞争绑定只有一条映射能成功；失败设备恢复
原地址时，将其保存到独立地址槽，保留未绑定成功的旧密钥，不以覆盖方式“修复”。
绑定返回超时后，先 GET 对账并复用已有本地密钥。没有服务器映射变更/自动换钱包
接口，后续需要换钱包时必须另做资金退出、双重证明和用户确认流程。

备份页面离线展示恢复词，离开/退后台清空可见内容；录屏/屏幕共享时隐藏，禁止
通过产品剪贴板按钮或网络分享恢复词。系统截图无法由这些措施彻底阻止，仍需真机
验证。完整重输只证明此刻用户能重现恢复词，不证明其备份永远安全；钱包删除、
系统密码移除、设备丢失后是否能恢复，必须用无价值测试钱包在物理设备验收。

目前收款 QR、Arbitrum 广播、HyperCore 可交易余额、入金对账、交易/提现执行均未
开放。**本地备份标记或地址绑定成功不能提升任何资金权限。**

## CCTP 路线与费用更新

本次直接读取 Circle 主网费用接口得到 `minimumFee=0`、转发费 `200000` 个 USDC
最小单位，即 0.20 USDC。这是一次实测，不是永久收费承诺；通用 CCTP 费率表与
特定 HyperCore 路线不能混用。客户端每次预览请求这一固定路线，超过 60 秒就
要求刷新，失败不回退到零费用。费率按精确十进制换算为百万分比，计算向上取整，
并单列 20% 最大费用缓冲，不把费用上限伪装成实际已经扣除。[^23][^26]

固定主网路线如下，地址来自 Circle 发布表，而非用户输入、网页脚本或服务端
任意传入参数：[^21]

| 原生 USDC | `0xaf88d065e77c8cC2239327C5EDb3A432268e5831` |

入金参数令 mintRecipient 与 destinationCaller 同时指向 CctpForwarder；56-byte
version-0 hook 内固定放当前 owner 地址与 DEX 0。DEX 0 是默认永续账户，不意味着
HIP-3 市场保证金自动可用。金额授权与 burn batch 金额相同，避免意外生成多笔。

`batchDepositForBurnWithAuth` 交易；授权本身不是单独发往 USDC 的交易。[^22]

CoreDepositWallet 源码也保留可配置的入金扣费分支。须结合实际配置和逐笔账目
验证，不能承诺“入金绝不扣账户费”。[^24][^46][^47]
本产品要求在 CCTP 费用上限之后至少保留 1 USDC，这是产品保护，不是协议最低额。
例如上述实测费率下，输入 10 USDC，仅扣预计 CCTP 费用后为 9.80、按最高 CCTP
费用计算为 9.76 USDC；两者都不是保证到账额，其他账户费用须另外核实，ETH gas
另计。测试网另有地址状态及额度限制，不能以任意新地址失败判定编码错误。[^24]

Circle 另有支持代付的 CctpExtensionV2，其授权 nonce 绑定完整转入参数，relayer
可以批量代付 gas。本轮不混用两个合约：自付 gas 走 CctpExtension，未来需要代付

receipt。此选择保留后续低摩擦入金体验，不要求本期部署或质押市场。[^25]

## 源链预检实现

### 同区块的余额与配置

读取余额不能只是请求一个数字。原生预检先确认 `eth_chainId=42161`，再取得
最新区块的 number/hash/timestamp/baseFee；余额、nonce、代码和合约 getter 使用
EIP-1898 `blockHash + requireCanonical=true`，完成后重读同高度区块，确认 hash
未改变。区块时间落后 60 秒、超前超过 15 秒或设备时间倒退均拒绝；快照最多保留
30 秒，过期后不能继续作为余额证据。[^28]

检查范围包括原生 USDC 的 6 位精度、暂停状态、owner/extension/minter 黑名单，
extension 的 token/tokenMessenger、TokenMessenger 的本地 transmitter/minter、
HyperEVM 域映射与 owner/extension denylist，transmitter 的本地域/暂停状态，
minter 的暂停状态与 burn 限额。五个合约必须有代码，并记录各自 runtime hash；
owner 必须是无代码 EOA，不把带 EIP-7702 委托代码的地址当成普通设备钱包。[^29]

“地址存在代码且 getter 匹配”仍不是独立安全审计。代理实现可能升级，RPC 也能
返回错误状态；正式开放前必须完成代理实现/源码/审计版本清单、变更处置及可靠
RPC 服务配置。当前官方公开 RPC 是无 SLA 的开发读取来源，不能单凭一次通过
宣布生产就绪。

### 精确金额与 gas

USDC 以 6 位最小单位、ETH 以 wei 处理，均支持完整 uint256。只允许规范 RPC
quantity 和严格 32-byte ABI word；不接受负数、科学记数法、空值、超宽整数或
把错误当成 0。BigInt 固定 5.7.0，提交为
`e07e00fa1fd435143a2dcf8b7eec9a7710b2fdfe`；金额乘法/上取整使用库整数运算，
结果超过 256 位直接拒绝。显示层使用十进制字符串，不经过浮点数。[^30]

gas 预检先验证 EIP-3009 签名对应这份不可变计划及同一 owner，然后检查授权未
使用/取消、真实 USDC、extension allowance、burn cap、未争用的 nonce。调用
`eth_call` 模拟原始 580-byte 入金 calldata，再用相同 calldata 估算 gas；
不会用假签名、零余额 override 或占位交易“估算成功”。当前部署合约会拒绝
`minFee()` 和文档中的 `getMinFeeAmount(uint256)` getter，因此不把这两个读取
失败当作“零费用”；由该部署合约的实际模拟执行检查它的费用约束。[^31]

Arbitrum 的 `eth_estimateGas` 已包括 L1 数据发布成本折合的 gas，不再重复加一次
L1 fee。产品预览给 gas 数量加 20% 上限缓冲，gas price 上限取所观察价格与该
区块 base fee 较高值的 2 倍，priority fee 为 0。另设 500 万 gas 和每笔
0.01 ETH 的产品安全限额，超过限额不自动增加用户支出。ETH 余额须覆盖整个
上限，最终再次检查 nonce、区块、报价和账户时效；这不是实际收费承诺，也不是
nonce 锁定。正式签名前仍需重新预检和记录待提交交易。[^32]

## 设备交易日志与中断恢复

日志写入 App Support 中独立的 `FundingJournal/transactions.sqlite`，不触碰研究
或服务端数据库，不需要生产迁移。它在正式密钥签名和广播之前提供必要的持久化
边界。后续固定用途签名和用户记录恢复入口见下节，真实提交器仍待完成。

### 已实现的行为

- 同一 owner 最多保留一笔未解决源交易，重复 intent ID 必须逐字段一致；已用
  EIP-3009 nonce 不分配给新意图。只有尚未开始签名的 prepared 可以直接取消。
- 先提交 signing 状态再发出签名许可；保存精确签名、完整交易字节及本地哈希后，
  再提交 submitting 状态并发出提交许可。重复请求不能领取第二次提交许可。
- RPC 返回的哈希必须与本地哈希完全一致；缺失/不同结果进入 uncertain，不当成
  未付款或到账成功。签名与提交中的记录不会因重启、过期或用户取消而清空。
- 签名已经生成但确认窗口过期，仍按原意图验证并留档；任务取消后的签名/提交
  回调也保存已发生的证据。它们不会延长有效期或恢复提交许可。错误文案不再沿用
  预检阶段的“没有发生转账”保证。
- 回放会重建原报价、金额、费用、EIP-3009 授权、580 字节调用内容与外层 EIP-1559
  交易，验证 owner 签名及哈希；仅仅 JSON 可解码并不代表历史记录可信。

### 存储与威胁边界

每条事件使用 CryptoKit AES-256-GCM，认证数据包含日志 UUID、序号和前一条摘要。
SQLite 只保存密文与摘要链；独立随机 256-bit 日志密钥与检查点保存在要求设备密码、
不可同步/迁移的 Keychain 项中，不复用钱包熵，不存助记词或钱包私钥。

SQLite 使用 DELETE rollback journal、`synchronous=EXTRA`、`fullfsync=ON`，设置后
读回确认；文件锁覆盖整个 SQLite + Keychain 操作，数据库写入使用绑定参数。
先把下一检查点写为 Keychain pending，再提交 SQLite，最后提升为 committed。
恢复时只接受旧 committed 或精确 pending 对应的数据库；不能匹配就停止操作，
不通过删除或新建空库掩盖问题。[^35]

目录/文件分别为 0700/0600，排除备份并配置 complete Data Protection；真机读回
保护级别和权限，不符合即拒绝继续。模拟器实际返回的 macOS 文件属性没有 iOS
保护级别，所以真机属性验收单独保留，不能把模拟器通过当作硬件保护已验证。[^36]

数据库回滚检测依赖仍可信的 Keychain 检查点，不能防止攻击者同时回滚两者或控制
已解锁进程。卸载、Keychain 丢失、双设备和电源中断仍需正式恢复方案与真机测试。
当前每次操作完整回放，最多 10,000 事件，每事件最多 16 KiB 明文；达到上限暂停
写入，不自动裁剪。长期留存、归档和大历史量性能是发布前未完成项。

**授权过期不等于交易字节失效**：EIP-3009 的过期校验属于合约层，外层 EIP-1559

## 2026-09-11：认证消息与目标链签名核对

### 本轮实现

- `CCTPMessageClient` 使用固定 Circle mainnet `/v2/messages/3`，只发送日志中
  的源链交易哈希。请求无账户凭据/签名/钱包密钥，不跟随重定向，响应限 32 KiB。
  严格区分完整消息、`pending_confirmations` 和标准 404；限流或错误不是交易失败。[^43]
- `CCTPAttestedMessage` 将 432 字节认证消息与源链消息比对，只允许 Circle
  填写 nonce、已执行 finality、费用和到期块。nonce 支持 bytes32 十六进制或精确
  十进制 uint256，必须与已签名消息相同；不使用浮点数。所有固定字节变更均拒绝。
- 签名使用 Keccak(message) 恢复，拒绝高 S、错误 v、重复或乱序 signer。
  `HyperEVMAttesterReader` 从固定 HyperEVM MessageTransmitter 读取实际 threshold
  与每位 signer 的启用状态，签名数必须恰好满足门槛，不按 API 公钥数量推算。[^44]
  16 个签名是客户端资源上限，不是协议门槛。
- 默认 HyperEVM RPC 仅支持 latest 合约状态。读取前后的 latest 块必须一致、
  足够新鲜，并验证 chain 999、domain 19 和 version 1；不使用不受支持的历史
  state 参数。合约暂停和 nonce 已使用单独记录，不推导 HyperCore 到账。[^45]
- 认证作为原加密日志的独立事件，绑定源交易、本次源链观察和前一次认证观察。
  新的源链观察使旧认证投影失效但不删除记录。中间出现 pending 也不丢失上次
  已验证的目标链状态，因此无法回退块高或把同一已使用 nonce 改成未使用。
- 历史页的显式跨链检查先刷新源链与账户注册，已返回的有效证据先持久化再处理
  页面离开/退出登录/任务取消。只呈现认证状态与费用，不显示原始签名，不开放

## 2026-09-11：目标链转发回执与费用口径

### 本轮实现

- `CCTPForwardObserver` 只读取已归档认证消息中记录的目标交易哈希，不搜索
  任意收款交易，也不广播、重签或自动重试付款。读取 chain 999、最新块、
  receipt、历史块和 nonce 状态，并复读交易/区块，拒绝不一致的快照。
- `CCTPForwardEventCodec` 从固定合约的日志逐项核对本条认证消息、owner、USDC、
  接收钱包、金额与 DEX。按 `MessageReceived` 到 `MintAndForward` 的区间关联，
  支持同一 relayer 交易有其他消息，但不允许借用另一条消息的事件。[^44][^48]

  已观察到账户费，不显示签名，不增加余额，不释放源链 nonce。

## Builder code 与真实委托预览（2026-09-11）

### 产品边界

bSmart 是 Hyperliquid 的交易前端，不是交易所或市场部署方。App 负责身份与本地
钱包体验、订单确认、签名提交适配和状态展示；订单撮合、仓位、保证金及清算以

授权，也不能套用订单的 L1 签名方案。用户可撤销，费率变更应重新展示并检查上限。
官方要求 builder 收款方拥有至少 100 USDC 永续账户价值并使用 standard 模式，

### 已实现的协议与预览

- `HyperliquidBuilderFee` 只接受明确的非零收款地址及 1 至 100 个 0.1bp 单位。
  `f=10` 对应 0.01%；永续上限为 0.1%。地址规范化后连同费率进入不可变委托。
- 订单 `builder` 对象包含在 MessagePack 与 EIP-712 签名摘要中；改变费率、地址
  或移除 builder 后，旧签名失效。官方 SDK 向量增至七组，新增带 builder code

- 真实 `l2Book` 使用原始价格，最多读取每侧 20 档，按买入/卖出方向遍历至限价；
  保留预计成交、未覆盖数量、均价及价格冲击，深度不足不虚构完整成交。

  市场费。bSmart builder fee 独立计算，不重复享受 referral、staking 或 growth
  折扣。市场费、应用费与总预估费分开保留。[^68]
- 预览同时受账户快照、订单到期及订单簿双时钟限制。订单簿最多 5 秒，网络耗时
  也计入；系统时间冻结或回退不能延长旧数据。卖出限价不是最高成交额，价格

## 出金记录与共享 nonce（2026-09-11）

本轮承接基本入金、出金和真实 IOC 订单，不改变 builder 尚未配置、生产资金
开关关闭的边界。代码落在现有 `Core/Trading/Funding`，未新建数据库或服务。

### 已实现

- `HyperliquidWithdrawalRecord/Journal` 将审核、签名开始、签名保存、提交开始、
  接受、拒绝或不确定结果写入既有加密、Keychain 锚定日志。API 接受不代表
  Arbitrum 已到账；该层既不读取设备私钥，也不发放签名或网络提交许可。
- `HyperliquidOwnerNonce` 统一订单和出金的 owner 序号；取消审核仍保留高水位。
  `nextOrderNonce` 兼容调用新方法。真正预约在同一文件锁内检查和写入，不能
  把读到的下一序号当作已预约。相同钱包跨应用账户 ID 也不能绕过冲突检查。
- 只有未签名审核可取消或本地过期。签名开始后，不因一小时、一天、重启或
  任务取消释放；未知结果不可重发，也不能用随后一次拒绝覆盖先前未知结果。
- 已被新记录取代的旧审核不能通过系统时间回拨重新进入签名阶段。签名或
  回执返回后，即使 UI 取消或时钟回拨仍持久保存；后者使用不倒退的本地记录
  时间，真正先后由日志序号确定，不冒充链上时间。
- 旧订单、授权和入金记录保持可恢复；订单与出金共用 Hyperliquid nonce，
  不与 Arbitrum EVM 交易 nonce 混用。

## 合约范围与原生减仓（2026-09-11）

现有真实下单入口原本只查询永续市场，本轮把用户明确的“仅合约”决策写入交易
产品文档与执行契约，并补上之前缺失的原生减仓/平仓操作：

- 按真实目标仓位选择 25% / 50% / 75% / 100%，自动决定买入平空或卖出平多。
- 固定 `reduceOnly=true`；部分数量向下取整，全部平仓保留交易所原始数量。
  微小余仓不为了满足开仓最低名义金额而放大；不承诺交易所必定接受或成交。
- 审核不签名。确认前和签名后重新读取仓位；方向、数量或杠杆变化都要求重新预览。
  签名后变化仍保存已有签名，不继续发送，也不改写原订单。
- 减仓允许滑点内的部分深度，展示预计成交/未成交数量；没有新的开仓保证金不自动
  阻止减仓。开仓仍保留原有完整深度与保证金/费用检查。
- 已解码的历史订单也需通过合约资产命名空间校验；现货资产 ID 和交易对不能用于下单。
- 继续使用现有设备签名许可、共享 nonce 和一次性提交，未修改生产开关，也未发送资金交易。

官方 Python SDK 的 `market_close` 同样从永续仓位确定方向和数量，并提交 reduce-only IOC；
此参考不构成真金验收或对最小余仓成交的保证。[^72]

验收记录：`/tmp/bsmart-perps-contract-only.xcresult`，iPhone 17 Pro / iOS 26.5，
130 项通过、0 失败、0 跳过。覆盖减仓规划、确认前及签名后仓位变化、部分 IOC 成交、
共享序号/日志、原协议签名向量，以及 5 项中英文、320/393pt、明暗与大字号布局。
渲染附件已检查；测试使用公开测试钥匙、模拟交易所响应及临时加密日志，没有真实下单。
`make arch-check terminology-check` 和 `git diff --check` 通过。

只做合约不会自动解决提现口径：统一账户仍共用抵押余额，CCTP 转发费用仍不是总费用。
本轮未完成真实可提额、完整出金费用与端到端资金到账验收，这些工作继续保留。
